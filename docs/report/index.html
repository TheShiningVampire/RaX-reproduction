Can RaX be reproduced from what the authors released?

We took the authors' released code and prompts, ran their agent ourselves on one simulated task (two robot arms finishing a Tower of Hanoi), and tested the program it wrote. This page says what we did at each step, whether each step helped or hurt, and lets you watch what the agent was thinking while the robot moved.

What it is doing

Scores at each stage

Success rate on DexJoCo's official test layouts. The program runs alone, with no agent and no retries. The first three rows use all 150 layouts; the perturbation rows use the first 75, where the unperturbed session-2 program also scores in the high 90s.

The paper reports one session per budget, with no repeats and no error bars. Our two numbers come from the same agent with 8 vs 14 practice episodes. The difference between them is the kind of session-to-session spread the paper does not measure.

The insight that made it work: one hand at a time

What the agent worked out: right first, then left

The right hand grasps the red disk first, then curls its two spare fingers out of the way. Only then does the left hand grasp the yellow disk. The hook shape and the lift test stay the same. To save time, the left arm moves while the right arm moves.

The right-hand grasp now holds on the first try on all 150 test layouts.

What it replaced: both hands closing together

In session 1 both hooks closed at the same moment. The left hand's straight fingers sat where the right index finger needed to go, so the right grasp often slipped. It failed on the first try on 58 of 150 layouts.

The agent found this itself, with no hint from us. In its third new practice episode (video 2 above) it looked at its own wrist-camera frames and saw the two hands' fingers in each other's way. It wrote the cause into its notes, rewrote the controller, and in the next episode (video 3) completed the whole tower with the new method.

Perturbations: does the final program survive a changed scene?

We changed one thing at a time and re-ran the final program, with no agent and no retries, on the first 75 official test layouts. Every perturbed run therefore has an unperturbed twin. Except for the new disk colours, each change is one of DexJoCo's own randomizers, switched on through a small opt-in hook we added to the harness. The rows go from physics, to appearance, to whether the program understands the task.

What the program handles

Heavier or lighter disks: 72/75. The new two-step grasp holds whatever the disk weight. A new table texture: 66/75, even a red wood table that could have confused its red-disk detector. New lighting: 53/75, still most of the time. The unperturbed program scores 73/75 on the same layouts.

What it was never asked to handle

A moved camera: 29/75. Camera, lighting and texture all together: 14/75. New disk colours: 0/75. In standard Hanoi practice the camera and colours never change, so the agent tuned colour thresholds for the one view it saw. When the view or the colours change a lot, the program cannot find the disks and does not start. That shows what it practised on, not the limit of the method. See "Giving it a fair chance" below; that test is running now.

Giving it a fair chance

The visual rows test the program on something it never practised. Before reading them as a weakness of RaX, three facts matter:

  1. Our runs had no Gemini. The paper gives the agent a vision-language model (Gemini 3.8 Flash, $10 per session) that it can call to locate objects. We had no key for it, so that tool was switched off. That is a deviation from the paper. Our agent also never tried to call it: 0 calls in about 1,000 tool calls.
  2. The authors' own Hanoi program also uses plain colour-and-depth code, even though Gemini was available to it. So on this task the agent chooses simple perception when it works. That is a sensible choice for the scenes it sees.
  3. The practice scenes decide what gets learned. Standard Hanoi practice only moves the tower a few centimetres. The agent had no reason to prepare for new lighting, a new camera angle or new colours, and its own "avoid-overfitting" skill cannot catch a variation it never sees.

The fair test is already built into the harness. An adaptation session lets the same agent keep practising on bimanual_hanoi_random, the official variant where camera, lighting and table texture change every episode, ideally with Gemini switched on. The question then becomes: when the agent does see visual variation, does it write perception that survives it? For new disk colours, the fair version is the same idea with colours varied during practice. A program that finds "the medium disk" by size, through depth or a well-phrased Gemini prompt, would pass.

Status: running now, without Gemini (we have no OpenRouter key). The same agent continues from session 2 with 6 practice episodes on bimanual_hanoi_random. Its briefing says: "This environment is the randomized variant … do not assume earlier poses or colors still hold." Its new program will be scored on 150 randomized layouts and compared with the current program's 14/75 on that setting, then re-tested on each single change above. Until then, the visual rows are marked "not practised yet" rather than as failures of the method.

The prompts, exactly

The agent's entire first message is two lines. Everything else it reads from files the harness writes into its workspace. All of them are rendered from templates in the repo, and we checked that the rendering matches the authors' recorded fingerprints byte for byte.

Read AGENTS.md, then MCP_SESSION.md and TASK.md, and call `status`. Follow the AGENTS.md
workflow.

TASK.md

"Execute the final two moves of the three-level Tower of Hanoi: move the medium disk from the middle peg to the right peg with the right hand, then move the small disk from the left peg to the right peg with the left hand." It also gives the robot, the cameras, the 1,500-step limit, "no partial credit", and 3 photos of the finished tower.

AGENTS.md and 25 skills

"Solve the task by hand first … The final evaluation is the formal batch: your submitted code run alone on held-out layouts." The skills cover hand control, depth perception, free dry-runs, and habits such as avoid-overfitting and rehearse-the-controller.

The VLM (Gemini) prompts are not fixed: the agent writes its own if it uses the tool. Neither our Hanoi programs nor the authors' published one call Gemini, so on this task nothing is missing.

Caveats

  • One task. We tested Hanoi only. The paper covers dozens of tasks across five benchmarks.
  • Session 2 departs from the paper. The paper always starts from an empty workspace. Our 54.7% is the faithful number; the second score shows what more practice buys.
  • No Gemini in our runs. The paper makes Gemini available ($10 per session). We had no key, so the agent could not use it. On standard Hanoi this changes nothing, since neither our programs nor the authors' published one call it. It may matter for the visual perturbations (see "Giving it a fair chance").
  • Small setup differences: Claude Code 2.1.303 instead of 2.1.296, a newer bubblewrap, and an RTX 6000 Ada for session 1.
  • Closed models change over time. An exact rerun is impossible even with identical code.
  • The activity logs are reconstructed. The agent's private reasoning is not stored. The lines come from its visible messages, tool calls and notes; inside program stages, line timing is approximate.
  • Cost: $54.66 in API for both sessions. Testing and perturbations cost GPU time only.
